StrajaBackupSQL - Updates and release publication

PUBLIC REPOSITORY
https://github.com/weblikero/straja-backup-sql
This repository is separate from weblikero/straja-backup (the Windows file backup product).

INSTALLED APPLICATION
Version 0.1.7 introduces update discovery. Earlier versions must be upgraded manually once.
With automatic checking enabled (default), the open GUI checks at startup when due and
then at most once every 24 hours. Last attempt is persisted across restarts. The tray
agent alone does not check for updates. Settings offers a manual check and opt-out.

A new release appears in an in-app banner. Skip this version dismisses that version
across restarts; a later version still appears. A manual check shows skipped updates
again.

Starting with 0.1.12, Download and install performs the update without opening a
browser. The application shows download percentage and transferred bytes, verifies
the installer, waits for the current backup, and hands off to Setup. The application
closes only for installation and reopens afterward. A previously running agent is
restarted; an agent that was already stopped is left stopped. Configuration and
backups are preserved. The check preference never silently authorizes installation:
the user clicks Download and install for the offered version.

Versions through 0.1.11 still open the release page. Install 0.1.12 manually once
to enable this workflow for later updates. In-app installation requires a normal
installed copy (not the portable build).

DOWNLOAD AND HANDOFF
Metadata is fetched afresh from the exact product's public stable GitHub tag.
The installer filename, version, HTTPS URL, SHA-256 digest and size must match.
Missing digests, previews, downgrades, other repositories and unexpected redirects
are rejected. Downloads stream to a unique folder in %LOCALAPPDATA%\StrajaSQL\updates;
the size is bounded to 512 MiB. Partial or corrupt content cannot become an installer.
Download cancellation leaves the application and running backups available.
Only GitHub and its official release asset CDN hosts may serve the download.

The verified installer is rehashed and held with a read-sharing lock during launch
and installation. A copy of the application's executable and its app-local runtime
performs the handoff from the cache directory, outside the installation directory.
Coordination locks prevent new agent starts/claims and new windows during handoff.
The current backup may finish for up to 24 hours; it is never force-terminated.
The updater also verifies that a running agent belongs to this installation.
Setup uses /SILENT with installation progress, /NORESTART, /NOCLOSEAPPLICATIONS and
/NORESTARTAPPLICATIONS. It targets the same directory and preserves installer tasks.
On installation failure the existing application and previously active agent are
restarted, and error details are written in the update's cache folder.
Windows restart requests are reported; the updater never reboots the PC.

SHA-256 from HTTPS GitHub metadata verifies integrity, not an independent publisher
signature. Builds currently remain unsigned. Keep the repository/account secure.
Automatic downloading or installation does not bypass Windows security checks.
Reference: https://jrsoftware.org/ishelp/topic_setupcmdline.htm
Asset metadata: https://docs.github.com/en/rest/releases/assets

UPDATE SOURCES, IN ORDER
1. https://api.github.com/repos/weblikero/straja-backup-sql/releases/latest
2. https://strajabackup.com/updates/strajabackupsql/windows-x64/stable.json

Since 0.1.10, a valid GitHub release is authoritative. When GitHub is missing,
inaccessible or invalid, the app tries the product-specific website feed.
Versions 0.1.7-0.1.9 still prefer the website: update or remove an old site feed
when publishing a new release so these clients can discover it too.
GitHub must return a non-draft, non-prerelease release tagged vMAJOR.MINOR.PATCH,
with an uploaded nonempty asset named:
StrajaBackupSQL-MAJOR.MINOR.PATCH-windows-x64-setup.exe
Tags without a release, draft releases and preview releases are not update offers.
If GitHub has no stable release and the website returns 404, Settings says the feed
has not been published. Network/server/format failures show a retry message; they
never report successful verification or affect backup jobs. Cached valid offers remain
available offline. An old website feed cannot hide a newer GitHub release in clients 0.1.10+.

Each source request has a 15-second total timeout, 5-second connection timeout,
256-KiB GitHub / 32-KiB website response limits, verified HTTPS and no redirects.
Worst case is two requests.
No GitHub token is bundled or requested from end users. Requests carry the product
and app version User-Agent plus normal HTTP/IP metadata; they contain no connection
names, database names, passwords, backups, Windows user names or machine identifiers.

FEED SCHEMA 1 (example only; do not publish a future version before its release)
{
  "schema_version": 1,
  "product": "strajabackupsql",
  "platform": "windows-x64",
  "channel": "stable",
  "version": "1.0.0",
  "release_url": "https://github.com/weblikero/straja-backup-sql/releases/tag/v1.0.0"
}

An alternative release_url is https://strajabackup.com/downloads/strajabackupsql/.
Use the real download page if hosting the installer on your own website. Other products
need their own product identifier, feed path, repository, installer and installation ID.
The current client rejects another product/platform/channel, unknown schema, prerelease
versions, unknown fields and release links outside these exact product locations.
Versions use semantic ordering: 1.10.0 is newer than 1.9.0. Equal/older versions and
changes only to build metadata are not offered. There is no automatic rollback.

PUBLISH A NEW VERSION
1. Increment Cargo.toml and installer default version; update the validation report.
2. Run the tests, localization generator, dependency notices and release packaging.
3. Test install/upgrade/uninstall and SQL restore on a separate clean Windows station.
   Complete publisher signing and redistribution review before a production release.
4. Commit the tested source, build the installer from that revision, then run:
   .\scripts\prepare-release.ps1
   The immutable kit records the source commit and hashes. Push that commit to GitHub.
   Write release notes in a UTF-8 text file describing changes and any limitations.
5. Validate and inspect the release without network access:
   .\scripts\publish-release.ps1 -NotesFile .\release-notes.txt -Channel stable -DryRun
   Upload a draft (not offered to installed clients):
   .\scripts\publish-release.ps1 -NotesFile .\release-notes.txt -Channel stable
   Publish the tested version, making it Latest:
   .\scripts\publish-release.ps1 -NotesFile .\release-notes.txt -Channel stable -Publish
   To publish a test version instead, use -Channel preview -Publish (the default
   channel is preview). Previews never notify stable clients.
   Requires an authenticated GitHub CLI with release-write access. No token is
   stored in the app. All files upload to a draft first. Every remote SHA-256 and
   size is verified before publication. Interrupted uploads can resume by rerunning
   the same command. Public versions cannot be overwritten by this script.
   The command uploads the installer, checksum, notices, documentation, manifest
   and corresponding SQL utility source archives. A Git push alone is not a release.
6. Optional website feed: run scripts/prepare-update-feed.ps1 -Version X.Y.Z.
   Upload the resulting dist/update-feed/updates/strajabackupsql/windows-x64/stable.json
   to the identical site path, AFTER the matching release/assets are publicly available.
   Use application/json, UTF-8 without BOM, Cache-Control: max-age=300 and atomic replace.
   Serve the exact URL directly over HTTPS; exclude it from HTML fallback routing and
   redirects. Other software feeds on strajabackup.com remain separate.
7. On a machine with an older version, select Settings > Check for updates and verify
   the offered version and release page. Also verify offline and skipped-version behavior.

The SHA-256 file is for checking downloaded artifacts; the app only discovers releases
and opens their pages. It does not download, hash, verify Authenticode or execute the
installer. HTTPS/feed validation is not a substitute for publisher signing.
Building/packaging alone never publishes a version. Only publish-release.ps1 with
-Publish makes a release public. The website feed is always uploaded separately.
